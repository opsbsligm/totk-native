# Linux 内存池候选路径

当前默认仍导入游戏内存。`TOTK_POOL_COPY=1` 才启用候选；`TOTK_POOL_IMPORT=1` 优先恢复导入路径。正式 Steam 入口尚未启用候选。

来源固定为 [UltraTears d657eff841e4](https://github.com/kuraeow/ultratears/blob/d657eff841e4ab80cd2aa4ba30f17d85f6402d9d/src/gfx/backend_vk.c)。上游说明 AMDGPU 对导入的 userptr 内存逐次提交进行逐页检查。本项目的 Deck 诊断也观察到提交线程较高的内核 CPU 时间及约 9.5 ms 的提交 ioctl；跟踪器有开销，这些数据不能作为优化后的帧率结论。

候选把池放进可映射、coherent 的 Vulkan 内存，64 MiB 块内分配，避免每个池创建一份驱动内存分配。Linux 6.7+ 的 `userfaultfd` 异步写保护和 `PAGEMAP_SCAN` 追踪 CPU 写页；不要求 root，不修改 sysctl、功耗或频率。提交前同步使用过的池，完成后按提交时快照合并 GPU 输出，再发布游戏事件和完成标志。较新的 CPU 字节保留，不能直接用 GPU 数据覆盖整块游戏内存。

本轮适配范围为集成 GPU，且不启用独立显存 shadows。不可读的虚拟池沿用现有 NVN 处理；重叠的实际池明确拒绝。缺少写监视、监视中途失效、分配失败或快照超预算时明确终止候选运行；退出实验变量可回到默认路径。每次 GPU 写范围的快照上限 16 MiB，全部在途快照合计 256 MiB，在途范围最多 65,536。没有吸收上游的冻结页/信号处理优化。

已对 `fcb2e36` 候选进行同一二进制、同一存档副本的导入→副本→导入 A/B/A，每轮连续采样 50 秒。该洞穴场景的呈现速率约为 27.34→60.01→32.27 FPS，队列提交 API 平均耗时为 24.98→0.18→20.46 ms；副本路径的帧间隔 p95 为 19.30 ms，第二轮导入还有一次约 952 ms 长帧。这支持该场景的提交瓶颈得到缓解，不能推断全地图稳定 60 FPS。测试保持原有 60 Hz/15 W，不修改内核设置。

2026-11-21 在部署版 `81f997f`（生产入口）上用 `tools/deck_pool_ab.py` 重跑同一二进制、同一存档副本的
导入→副本→导入 A/B/A，每轮连续采样 50 秒，场景是初始空岛草地（与上面的洞穴场景不是同一处，绝对帧率不可跨场景比较）。
呈现速率 20.93→29.67→19.46 FPS；队列提交 API p50 为 26.63→0.29→30.54 ms，长帧（>50 ms）178→4→539 帧。
同一场景的 A/B/A 复现说明差异来自池内存的提交方式，不是采样漂移：导入路径每帧提交都在内核逐页检查，导入臂 50 秒采样里全进程
内核 CPU 时间为 50.3 与 51.8 秒（翻译线程各 29.0 与 30.8 秒），副本臂同一窗口只有 16.0 秒（翻译线程 3.6 秒）。副本路径把这笔
开销消掉了。
副本路径的帧间隔 p50 从 46.84 ms 降到 32.72 ms、p95 39.72 ms，仍高于 60 帧所需的 16.7 ms：出图节拍已是每帧一次
（`@present_effective_ticks` 全为 1），限制在 CPU 侧而非显示同步。该场景每帧 7406 次绘制、485 个 render pass、3042 个
barrier，而整段提交的 GPU 时间只有 3.9 ms，瓶颈在录制与状态记录；把录制线程从 4 个加到 8 个不改善（29.04 FPS），说明不是
并行度不够。这段场景不是 60 帧场景，不能据此推断全部地图的帧率。
`TOTK_POOL_MEM=uncached` 与 `=device` 在该机不可用：帧率 2.57 与 2.97 FPS，进程内存分别多 200 MB 与 140 MB；副本继续用默认
缓存主机内存。测试保持原有 60 Hz/15 W，不修改内核设置；`hardware_validated=false`。

同一候选的系统菜单→返回标题→重载存档，以及月步开启/全部关闭后重复跳跃的写入计数检查已通过；237 个原始存档摘要不变。复审补充了同地址重建内存池的身份回归：旧在途范围不能影响新缓冲区的首次填充与后续脏页同步。此后代码变更仍须重新验证。

后续复审对 `6a3e6d2` 的生产 C 做了两个确定性交错注入：CPU 在快照比较与整块写回之间更新、
以及在 GPU 写观察清除窗口更新。两项旧实现分别丢失新值或漏掉下一次同步，不能据此前短样本
认定并发正确。修复使用对齐 64 位比较交换，冲突、不对齐前缀和尾部按字节比较交换；GPU
未改变的字节不写入。清除 GPU 写观察后显式标记整个写回范围，避免遗漏并发 CPU 写入；
失去跟踪或缺少快照时明确失败。该标记会增加后续同步量，须重新测量性能。
快照仍按值比较，不能识别写入相同值后又回到原值的意图；游戏应遵守原有 GPU 完成同步协议。

正式启用前仍需精确 HEAD 的完整 CI/安全审查、更多地图与切场景、长时运行及睡眠恢复验证。实体按键、物理触屏与陀螺仪方向没有以软件遥操替代验收，`hardware_validated=false`。
